Priority and ownership justification:
Priority 1 is highest in micro T-Kernel. Priorities 1–4 belong to the kernel (initial task 1, USB console 3, WiFi 4), so application tasks start at 7. Values 5–6, 13 and 15+ are left free for later tasks.


Within each core, periodic tasks follow rate-monotonic order (shorter period → higher priority). Core 1: vehicle_ctrl_task (7, sporadic) > line_task 10 ms (8) > motion_task 20 ms (9) > barcode_task (12, event). Core 0: the kernel's WiFi task (4) > imu_task 20 ms (10) > obstacle_task 60 ms (11) > telemetry_task 500 ms (14). Tasks on different cores do not preempt each other, so motion_task and imu_task sharing a 20 ms period only interact through mtx_odom, where TA_INHERIT bounds the wait to one struct copy. 


vehicle_ctrl_task (7) is sporadic and short (a state transition plus one mailbox send), so placing it above all periodic tasks costs little CPU but guarantees that a mode change (stop, obstacle, fault) is acted on within one dispatch. barcode_task (12) is low because the time-critical part, edge capture, is already done in gpio_isr; decoding has hundreds of milliseconds before the junction is reached.


Core placement is based on the template repo: cyw43_utk_task and the USB console task are created with assprc = TP_PRC1 (core 0) in cyw43_utk_kernel.c and usb_console.c. The control loop (vehicle_ctrl, line, motion, barcode) is pinned to core 1 (TP_PRC2) so network bursts on core 0 cannot preempt it. Slower sensing (IMU, ultrasonic) and telemetry run on core 0.


The emergency-stop path does not depend on priority order: obstacle_task and imu_task set MF_ESTOP in flg_motion directly, and motion_task polls it at the start of every 20 ms cycle. A busy vehicle_ctrl_task cannot delay braking.


Ownership follows TEAM.md Section 3 (one owning task per peripheral): ADC → line_task, I2C0 → imu_task, PWM slices 4–5 → motion_task, PWM slice 6 → obstacle_task, IO_IRQ_BANK0 → one shared gpio_isr (agreed shared file, see Appendix B), radio → kernel. Shared data is protected by mutexes created with TA_INHERIT (priority inheritance) and held only to copy a struct. Deviation from TEAM.md: the template's default bands (S1 12–13 … S5 20–21) follow folder number, not criticality. The team proposes the values above and will record them in TEAM.md Section 4 by agreement. All values are preliminary until NFR11 timing logs confirm them.
4. Task Interaction Diagram


  

(Task interaction diagram, Section 4)
Brief explanation of the main communication paths:


P1 Line-following loop (core 1): cyc_line wakes line_task every 10 ms → ADC read → PD steering Δv written to steer_sp under mtx_steer (owned by S2) → motion_task reads it each 20 ms cycle and adjusts the left/right PWM. steer_sp is latest-value data, so a mutex-protected struct is used instead of a queue. Stale corrections are worthless, so queueing them would only add lag.


P2 Barcode path: barcode DOUT edges (GP6) → gpio_isr stores (t_us, level) in the bc_edges[64] ring buffer and signals sem_bc on the first edge → barcode_task waits for a quiet gap, decodes, and sends NAV_MSG to mbx_nav (owned by S5) plus EV_BARCODE in flg_mission. A mailbox is used because every decoded command must be delivered exactly once.


P3 Command execution: vehicle_ctrl_task waits on flg_mission (OR of all EV_ bits), reads mbx_nav with TMO_POL, then sends MOVE/TURN/FOLLOW/STOP as MOTION_CMD to mbx_motion. motion_task sets EV_MOTION_DONE when a move completes. Line following is enabled or put into search mode with flg_line, and scans are requested with flg_obst.


P4 Emergency stop (red): obstacle_task (distance < 15 cm in 2 consecutive pings) and imu_task (horizontal gravity-removed acceleration |a_xy − a_xy_lp| > 1.0 g in any FIFO sample)  set MF_ESTOP in flg_motion directly. motion_task polls it first in every cycle and brakes, without waiting for vehicle_ctrl_task. Only vehicle_ctrl_task may clear it. Before the stop, obstacle_task sets EV_OBSTACLE_NEAR in flg_mission when three pings read under 35 cm, and vehicle_ctrl_task halves the speed through mbx_motion, so the robot reaches the 15 cm stop slowly and the scan starts closer to the obstacle. 


P5 Hump measurement and motion monitoring: motion_task publishes odom (count_l, count_r, dist_mm, speed_mms) under mtx_odom. Every 20 ms imu_task copies odom and derives Δs, the forward acceleration a_fwd (change in edge-timed speed over 100 ms)  and the turn rate from the wheel-count difference. It burst-reads the accelerometer FIFO over I2C0, computes pitch with a_fwd removed, and integrates h += sin θ · Δs to track the peak. It publishes terrain (pitch, hump state, peak, hump count, motion class, turn rate) under mtx_terrain, and sends hump reports and motion-class changes to mbf_event. 


P6 Telemetry: telemetry_task copies each subsystem's status through getter functions (each takes that subsystem's mutex briefly), drains mbf_event, serialises JSON (up to 160 bytes), and sends it to mbf_telemetry with TMO_POL. The MQTT code inside cyw43_utk_task polls mbf_telemetry with TMO_POL and publishes each message on the topic named by its first byte (Appendix B). MQTT commands go the other way, from mbf_cmd to telemetry_task, which turns them into EV_START, EV_STOP or EV_RESET. Between periods, telemetry_task waits on mbf_cmd between periods, so a command is forwarded as soon as it arrives, not at the next 500 ms tick. No student task calls cyw43, lwIP or MQTT functions (Section 3 of TEAM.md).


Hardware vs software vs ISR: grey boxes are hardware, hexagon/orange boxes are interrupt-level code (gpio_isr, cyclic handlers), and rounded boxes are tasks coloured by core. Each kernel object is labelled with the subsystem that creates it (the receiver/owner, per TEAM.md Section 5).
5. System-Level Statechart
  

(System-level statechart, Section 5)


Elaboration on main states and any important assumptions:
IMU identity over I2C0 (the magnetometer's IRA/IRB/IRC_REG_M must read 'H','4','3'; the LSM303DLHC accelerometer has no WHO_AM_I register, so it is checked by writing CTRL_REG1_A and reading it back). If only the IMU checks fail, the run still starts, with Region B in IMU_DEGRADED and an IMU_WARN event; any other self-test failure goes to FAULT. .


CALIBRATING runs in two steps, because the IMU needs the robot still and the IR sweep needs it moving. First the IMU offset: 2 s stationary on level ground, averaging the accelerometer to get the pitch and roll offsets. Then the IR sweep: line_task collects min/max while the robot sweeps over the line (≤ 3 s). If the black/white contrast is below 800 ADC counts the system faults, because thresholds would be unreliable (FR2, FR18).


READY: motors braked, line following disabled. EV_START comes from the GP20 button or an MQTT START command. Remote input only starts or stops the run; it never steers (FR1 autonomy).


RUNNING has three orthogonal regions. Region A (mission) is the only one that changes motion: LINE_FOLLOWING → APPROACH_JUNCTION (after a valid barcode) → EXECUTING_COMMAND → REACQUIRE_LINE → LINE_FOLLOWING. OBSTACLE_AVOIDANCE is entered on EV_OBSTACLE from any Region A substate (LINE_FOLLOWING, APPROACH_JUNCTION, EXECUTING_COMMAND, REACQUIRE_LINE, LINE_RECOVERY). A pending barcode command is discarded and logged, and after EV_LINE_FOUND the mission returns to LINE_FOLLOWING. LINE_RECOVERY handles line loss with ≤ 3 retries. Region B (terrain: FLAT/ON_HUMP) and Region C (link: OFFLINE/ONLINE) run in parallel and never block the mission, so the robot keeps driving with no WiFi or with a degraded IMU.


FAULT is reachable from every RUNNING substate (EV_IMPACT, stall, sensor fault, line not found after 3 retries, no bypass path). Entry action: MF_ESTOP set, motors braked, buzzer pattern, fault code published. Recovery needs a deliberate action (GP20 held 2 s or MQTT RESET) and the fault cause cleared, so a transient glitch cannot restart the motors. A fault raised in INIT or CALIBRATING returns to INIT, so self-test and calibration run again; a fault raised while RUNNING returns to READY with the motors braked.


FINISHED is entered on EV_STOP or the course end condition. How the course end is signalled is not given in the brief (assumption A12, decision D3). The run summary (peak hump height, barcodes decoded, run time) is published there.


Key assumptions: a barcode always precedes the junction it refers to by a fixed, measurable distance d_junction (A11), and only one command is pending at a time (a new barcode overwrites an unexecuted one and is logged).
6. Subsystem Statecharts
6.1 Subsystem Statechart 1
* Subsystem name: Line Following (S3 - Buddy 3)
* Related RTOS task(s): line_task (pri 8, core 1, 10 ms); cyc_line
* Purpose: Keep the Centre IR sensor on the line edge with PD steering; detect junctions and line loss; perform line search when commanded.
* Reason a statechart is needed: Its behaviour depends on history, not only the current reading: the same 'both sensors white' reading means a brief wobble in TRACKING but line loss after 30 mm, and steering must be held during JUNCTION. A state machine makes these distance-based timeouts and the hand-over with vehicle_ctrl_task (LF_ENABLE / LF_SEARCH) explicit and testable.
  

(Line Following statechart, Section 6.1)


Brief explanation of states, events, and fault handling:
DISABLED is the safe default (steer_sp = 0), entered whenever vehicle_ctrl_task clears LF_ENABLE, e.g. during turns.


CALIBRATING records each sensor’s white and black level, so readings become n = 0 (white) to 1 (black). Two levels are used: BLACK means n > 0.75 and WHITE means n < 0.25. One midpoint threshold would fail, because the Centre sensor sits on the line edge at about 0.5.


TRACKING: the Centre sensor rides the line edge. A PD controller turns the error e = n_C − 0.5 into a steering correction for motion_task. If the robot overshoots (Left BLACK, Centre WHITE), it steers hard left.


JUNCTION: Left BLACK while Centre is not WHITE, for ≥ 15 mm → EV_JUNCTION. LOST: both WHITE for ≥ 30 mm → EV_LINE_LOST. The last Centre reading shows which side the line is on. In SEARCHING, vehicle_ctrl_task turns the robot and counts retries; when Centre is no longer WHITE → EV_LINE_FOUND.


Faults: calibration contrast below 800 counts, or a reading more than 20 % outside the calibrated range for 0.5 s → SENSOR_FAULT, latched until RESET.
6.2 Subsystem Statechart 2
* Subsystem name: Barcode Decoder (S3 - Buddy 3)
* Related RTOS task(s): gpio_isr (GP6 edges) + barcode_task (pri 12, core 1)
* Purpose: Capture bar/space widths at µs resolution, decode Code 39 '*X*' frames read in either direction, and publish exactly one NAV_MSG per barcode.
* Reason a statechart is needed: Decoding is a sequence-dependent protocol (arm → capture → quiet-gap → decode → publish → cooldown). Without explicit states the same barcode would be read twice, partial frames would be decoded, or edges seen while the robot is turning across the line would produce false commands.


  

(Barcode Decoder statechart, Section 6.2)
Brief explanation of states, events, and fault handling:
The barcode is Code 39 *X*, verified from the sample PDF: 29 elements, of which 3 in every 9 are wide. A narrow element is about 3 mm.

ARMED: gpio_isr timestamps every edge on GP6, ignores flips under 0.5 ms (sensor flicker), and wakes barcode_task on the first edge. CAPTURING ends when no edge arrives for max(60 ms, 4 × widest element).


DECODING: the 3 longest elements in each group of 9 are wide, so robot speed cancels out. The shortest wide element must be ≥ 1.8 × the longest narrow one. If '*' isn't found, the list is reversed in case the barcode is printed the other way round.


A valid frame → PUBLISH: the command goes to mbx_nav with EV_BARCODE. COOLDOWN then ignores edges for 200 mm so the same barcode isn’t read twice. Clearing LF_ENABLE disarms the decoder from any state, so turns can’t create commands.


Faults: more than 64 edges or an invalid frame → REJECT, logged, with no motion change. The robot keeps following the line, so a failed read never causes a wrong turn.
6.3 Subsystem Statechart 3
* Subsystem name: Motion Control (S2 - Buddy 2)
* Related RTOS task(s): motion_task (pri 9, core 1, 20 ms); encoder part of gpio_isr; cyc_motion
* Purpose: Closed-loop wheel speed control and encoder-based MOVE / TURN execution for every other subsystem.
* Reason a statechart is needed: The meaning of a cycle depends on the active command (follow vs fixed distance vs in-place turn), and the emergency-brake latch must override every motion state until it is explicitly cleared.




  

(Motion Control statechart, Section 6.3)


Brief explanation of states, events, and fault handling:
In IDLE_BRAKED, both motor inputs are set low for active electrical braking (Robo Pico truth table). It transitions to FOLLOWING on MOTION_CMD FOLLOW, to MOVING_DIST on MOTION_CMD MOVE, or to TURNING on MOTION_CMD TURN. In FOLLOWING, closed-loop steering applies base speed ± steer_sp from line_task. Receiving MOTION_CMD STOP returns to IDLE_BRAKED.


MOVING_DIST executes PID control until reaching target encoder distance dist_mm, then posts EV_MOTION_DONE and returns to IDLE_BRAKED. TURNING executes in-place rotation until ticks match target arc length arc = (θ · π · track) / 360°, posts EV_MOTION_DONE, and returns to IDLE_BRAKED. Receiving MOTION_CMD STOP in either state forces an immediate return to IDLE_BRAKED.


ESTOP_BRAKED latches on MF_ESTOP from any moving state (checked every 20 ms cycle), sets motor outputs low (GP8–GP11 low), and discards every mbx_motion message that arrived before CLEAR. CLEAR is accepted only after vehicle_ctrl_task has cleared MF_ESTOP. motion_task then returns to IDLE_BRAKED and executes the messages queued after CLEAR in order, so "CLEAR, TURN 45°" sent together works.
STALL_FAULT triggers from any moving state if PWM duty ≥ 40% with 0 encoder counts for 300 ms. Entry action brakes the motors (GP8–GP11 low), sets MF_ESTOP and posts EV_FAULT (STALL); it then waits in ESTOP_BRAKED for CLEAR like any other stop. 
Implementation &amp; Interface Protocols: Single-channel encoders on GP16/GP17 count tick edges without direction sensing, so motion_task explicitly applies the active command sign to odometry (Δs) for reverse moves (e.g. REVERSE_RETRY -100 mm). Stall monitoring guards all moving states, and receiving CLEAR unconditionally flushes mbx_motion to prevent stale command execution upon recovery.
6.4 Subsystem Statechart 4
* Subsystem name: Obstacle Scan, Avoidance and Line Recovery (S5 - Buddy 5)
* Related RTOS task(s): obstacle_task (pri 11, core 0) + vehicle_ctrl_task (pri 7, core 1); echo part of gpio_isr
* Purpose: Detect an obstacle on or near the line, slow down and stop, profile it with a coarse then fine servo scan, choose continue / left / right / reverse / stop, drive the bypass and hand control back to line following. 
* Reason a statechart is needed: The write-up defines a staged process (coarse scan → fine scan → profile → plan → bypass → recover). Each stage has its own exit conditions and retry limits, and the same distance reading means different things in MONITORING (is something ahead?) and FINE_SCAN (where is its edge?). A statechart makes those stages and their failure exits explicit and testable. 


  

(Obstacle Scan, Avoidance and Line Recovery statechart, Section 6.4)
Brief explanation of states, events, and fault handling:
Ranging: obstacle_task drives TRIG high for 10 µs, then waits up to 30 ms on OB_ECHO in flg_obst (TWF_ORW + TWF_BITCLR). gpio_isr timestamps both ECHO edges and sets OB_ECHO on the falling edge. An ECHO pulse longer than 25 ms, or no falling edge within 30 ms, means nothing within 4 m: path clear, not a fault. The stop check uses raw pings (two in a row under 15 cm) to avoid median filter delay, and applies from both MONITORING and SLOW. 
MONITORING → SLOW → STOPPING: with the servo at 90°, three pings under 35 cm set EV_OBSTACLE_NEAR, and vehicle_ctrl_task halves the speed (write-up: "stop or slow down"). 40 cm or more returns to MONITORING and sets EV_OBSTACLE_CLEAR, so vehicle_ctrl_task restores full speed; the 5 cm gap stops the state flickering. Two consecutive pings under 15 cm set MF_ESTOP and EV_OBSTACLE, so motion_task brakes within one 20 ms cycle without waiting for vehicle_ctrl_task (NFR6).
COARSE_SCAN: on OB_SCAN_REQ the servo visits 30°, 60°, 90°, 120° and 150°. Each reading becomes a point in the robot frame, x = d·cos θ and y = d·sin θ (x = sideways offset, positive to the right; y = distance ahead). Servo 30° points to the robot's right and 150° to its left (checked in S5-U03). If every hit (a reading under 40 cm) has |x| greater than half the robot width + 50 mm on the same side,the obstacle is near the line but off the robot's path. obstacle_task sets EV_OBSTACLE_CLEAR, and vehicle_ctrl_task clears MF_ESTOP, sends CLEAR and resumes FOLLOW. 
FINE_SCAN and PROFILING: the servo sweeps 5° steps across ±15° of the hit sector, out and back. Edges are where the range jumps by more than 10 cm. Each edge angle is moved inward by half the measured beam width, because the 15° HC-SR04 beam sees an edge early (A16). Width W = √(dL² + dR² − 2·dL·dR·cos(θR − θL)), by the law of cosines. If the two sweeps disagree by more than 10 %, FINE_SCAN repeats once. The result goes to obst_profile with EV_PROFILE_READY.
PLAN, BYPASS and SEARCH_LINE are executed by vehicle_ctrl_task, because they command motion and mbx_motion has one sender. Before any motion leaves STOPPING (continue, bypass or reverse), vehicle_ctrl_task first clears MF_ESTOP in flg_motion (tk_clr_flg) and then sends CLEAR to mbx_motion, so motion_task leaves ESTOP_BRAKED. A side is chosen only if its clearance ≥ robot width + 50 mm. BYPASS sends TURN 45° away from the obstacle, MOVE out (enough for the chosen clearance), TURN −45° to drive parallel to the line, MOVE past the obstacle (its width + robot length + 50 mm), then TURN −45° back toward the line. After EV_MOTION_DONE, SEARCH_LINE sets LF_SEARCH until EV_LINE_FOUND, then hands control back to line_task.
Faults: if no side is clear, REVERSE_RETRY moves back 100 mm and rescans, at most twice, then NO_PATH. No line within 300 mm after the bypass is LINE_NOT_FOUND. Echo stuck high or 5 invalid pings is SENSOR_FAULT. All three raise EV_FAULT and the system enters FAULT. EV_IMPACT from imu_task in any state centres the servo and aborts. Every transition logs {state, d, θ, decision} to mbf_event (FR16).
6.5 Subsystem Statechart 5
* Subsystem name: IMU Motion and Terrain Monitoring (S4 - Buddy 4)
* Related RTOS task(s):imu_task (pri 10, core 0, 20 ms), woken by cyc_imu. Reads odom (S2); writes terrain, MF_ESTOP (flg_motion), EV_IMPACT (flg_mission) and mbf_event. 
* Purpose: Calibrate the IMU, track pitch, detect humps and measure the peak hump height, detect impacts, derive turn rate and classify motion for telemetry.
* Reason a statechart is needed: A hump is a sequence (climb → crest → descend), and peak height only means something over that whole sequence. Sample-count hysteresis stops motor vibration creating false humps. The impact latch and the degraded mode must override every terrain state, and a statechart makes those overrides explicit and testable.


  

(Hump Detection and Terrain Monitoring statechart, Section 6.5)
Brief explanation of states, events, and fault handling:
Sensor set-up. The LSM303DLHC powers up in power-down mode at ±2 g, so imu_task's init writes CTRL_REG1_A = 400 Hz with X/Y/Z enabled, sets CTRL_REG4_A = ±8 g with high resolution and block data update, and puts the FIFO in stream mode. Every 20 ms cycle it burst-reads all new samples (about 8) in one I2C transaction of about 1.2 ms. The sensor has no gyroscope, so pitch comes from the accelerometer alone.
CALIBRATING. With the robot still and level, imu_task averages 2 s of samples for the pitch and roll offsets, then sets terrain.cal_done = 1. vehicle_ctrl_task starts the IR sweep only after it reads cal_done = 1 (or after 3 s with an IMU_WARN if the IMU is degraded). Roll φ = atan2(a_y, a_z) is reported in terrain for telemetry only.
Pitch and height. The samples are low-pass filtered. The robot's own forward acceleration a_fwd is subtracted. It is the change in speed_mms over the last 100 ms (5 odom samples), where motion_task measures speed from the time between encoder edges (gpio_isr already timestamps them at 1 µs), not from counts per 20 ms. a_fwd passes through the same low-pass filter as a_x so the two stay aligned in time: sin θ = (a_x − a_fwd) / g, minus the offset. Height is integrated as h += sin θ · Δs with encoder distance Δs, so it does not depend on speed and stops changing when the robot stops. The last 3 samples of Δh are buffered, so the climb that happens before CLIMBING is confirmed is added back rather than lost. h is reset to 0 in FLAT, so a small pitch offset cannot build up between humps.
Hump states. Enter CLIMBING when θ > +5° for 3 samples, go to DESCENDING when θ < −5°, and go to REPORT when |θ| < 3° for 5 samples. A climb whose peak is under 5 mm returns to FLAT as a false trigger. REPORT increments hump_count, updates the run peak peak_mm = max(peak_mm, h_max), publishes terrain and sends a HUMP event to mbf_event. Here a sample is one 20 ms filtered pitch value, not a raw 400 Hz FIFO sample. If CLIMBING or DESCENDING lasts more than 1 m of travel without completing, imu_task returns to FLAT and sends HUMP_ABORT to mbf_event, so a long slope cannot leave the state machine stuck. 
Short humps. Chassis pitch follows the hump surface only when the hump is longer than the wheelbase L. On a shorter hump, the integrated h is the average height under the wheelbase and reads low. imu_task therefore also records θ_max and reports L · sin θ_max. S4-U02 decides which estimate is used (A17).
Impact. Any FIFO sample with |a_xy − a_xy_lp| > 1.0 g (x and y only, gravity removed, preliminary) sets MF_ESTOP in flg_motion directly and EV_IMPACT in flg_mission, from any state. z is left out because hump edges jolt the robot vertically, while a collision decelerates it horizontally. IMPACT is left when imu_task sees that vehicle_ctrl_task has cleared MF_ESTOP (imu_task reads flg_motion with tk_ref_flg at the start of each cycle).
Turn rate and motion class. ω = (v_R − v_L) / track width comes from the encoder counts in odom (A7). Motion class runs alongside the hump states: STATIONARY (|speed| < 10 mm/s), ACCELERATING (|a_fwd| > 0.2 m/s²), TURNING (|ω| > 30 °/s), MOVING otherwise. CLIMBING_HUMP, DESCENDING_HUMP and IMPACT override these. A class must hold for 5 samples (100 ms) before it is reported. Changes go to mbf_event, and the current class and ω go in terrain (all thresholds preliminary, S4-U05).
Faults. An I2C error after 3 retries → IMU_DEGRADED. Hump, tilt and impact data are unavailable, terrain.imu_ok = 0, and an IMU_WARN event goes to mbf_event. It does not set EV_FAULT, because hump measurement is not safety-critical and the obstacle stop still protects against collisions. imu_task retries the init every 1 s and returns to FLAT when the chip responds, keeping the stored offsets.
6.6 Subsystem Statechart 6
* Subsystem name: Telemetry and Command Link (S1, Buddy 1)
* Related RTOS task(s): telemetry_task (pri 14, core 0) and MQTT code in cyw43_utk_task (kernel, pri 4), which runs the broker-connection states
* Purpose: Keep the robot connected to WiFi and the MQTT broker, publish telemetry and heartbeat, forward START/STOP/RESET, and recover from WiFi or broker loss without affecting control.
* Reason a statechart is needed: Link availability changes at run time and each state has a different buffering policy. Making it explicit shows that no network state can block a control task, and that every network failure has a defined recovery path (write-up: “implement connection recovery”).


  
(Telemetry and Command Link statechart, Section 6.6)


Brief explanation of states, events, and fault handling:
OFFLINE and ONLINE are read from cyw43_utk_get_status(), which the template documents as safe from any task. The broker session (MQTT_CONNECTING, ONLINE, BACKOFF) is tracked by Buddy 1’s MQTT code inside cyw43_utk_task. It is read by telemetry_task through a getter, and telemetry_task never calls cyw43, lwIP or MQTT functions. 


If the WiFi link drops, every state returns to OFFLINE and cyw43_utk_task rejoins. The public port only joins once at start-up, so this must be checked in the template (A14). If the broker refuses, times out after 5 s or misses keep-alive, BACKOFF waits 1, 2, 4, then 8 s before reconnecting, and goes back to 1 s after a successful connection. This stops a flaky network from causing a flood of reconnects. The connect message sets a retained last-will of "offline", so the dashboard knows the robot has dropped even when the robot cannot tell it.
Every send uses TMO_POL. If mbf_telemetry is full, the sample is skipped and drop_count is incremented (BUFFER_FULL). The newest snapshot is regenerated next period, so dropping old snapshots loses nothing important. Discrete events wait in mbf_event (2048 B, about 30 events) until drained; when it is full the event is dropped and counted. 
Commands are only START, STOP and RESET, so remote input can never steer the robot (autonomy requirement). RESET only sends EV_RESET. vehicle_ctrl_task owns the MF_ESTOP latch (IF-05). It checks that the fault has cleared, then moves from FAULT to READY with the motors braked. A new START is needed to move.

	Rejected with reason

	9. Design Consistency


Which task owns each hardware device?


line_task (S3): Left/Centre IR via the ADC (sole ADC owner). gpio_isr + barcode_task (S3): barcode DOUT GP6. motion_task (S2): motors GP8–GP11 (PWM slices 4–5) and encoders GP16/GP17 (via gpio_isr). imu_task (S4): LSM303DLHC on I2C0 GP4/GP5. obstacle_task (S5): HC-SR04 GP2/GP3 (Grove 2) and servo GP12 (PWM slice 6). vehicle_ctrl_task (S5): button GP21, buzzer GP22, and GP20 events via gpio_isr. cyw43_utk_task (kernel): WiFi radio GP23/24/25/29, with Buddy 1's MQTT code inside it. telemetry_task (S1) owns no hardware. Each device in Section 2 has exactly one owning task, listed above, matching TEAM.md Section 3. 


Which task has the highest priority, and why?


Among application tasks, vehicle_ctrl_task (7, core 1): it is sporadic and short, and every mode change (obstacle, fault, barcode command) must be acted on within one dispatch. Above it are only the kernel (USB 3, WiFi 4) and gpio_isr. Within each core the periodic tasks follow rate-monotonic order: core 1 line 8 (10 ms) > motion 9 (20 ms); core 0 imu 10 (20 ms) > obstacle 11 (60 ms) > telemetry 14 (500 ms); barcode_task is 12 because its timing-critical work is in the ISR. Braking does not rely on priority: MF_ESTOP is polled by motion_task every cycle.
